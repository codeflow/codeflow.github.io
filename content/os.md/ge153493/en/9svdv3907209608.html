🔒 Process Synchronization

🕐 2025-02-20 09:35:00 👨‍💻 @rafaelsantos
📚 About: Process synchronization is a mechanism that ensures multiple processes coordinate their execution to avoid race conditions, maintain data consistency, and prevent deadlocks. It involves concepts like critical sections, mutual exclusion, semaphores, and synchronization algorithms.

🟢 📚 What is Process Synchronization?

Process synchronization is the coordination of multiple processes to ensure they execute in a controlled manner, preventing conflicts when accessing shared resources. In a multi-process environment, processes may need to access shared data, files, or hardware resources simultaneously, which can lead to inconsistent states or incorrect results.

The primary goal of process synchronization is to:

  • Prevent race conditions: Ensure that processes don't interfere with each other when accessing shared resources
  • Maintain data consistency: Guarantee that shared data remains in a valid state
  • Coordinate execution: Control the order in which processes access critical resources
  • Avoid deadlocks: Prevent situations where processes are waiting indefinitely for each other

🟢 📚 Race Conditions

A race condition occurs when the outcome of a program depends on the relative timing of events, such as the order in which processes execute. When multiple processes access and modify shared data without proper synchronization, the final result may be unpredictable and incorrect.

Example Scenario: Two processes (P1 and P2) are both trying to increment a shared counter variable. Without synchronization:
  • P1 reads counter = 5
  • P2 reads counter = 5 (before P1 writes)
  • P1 increments and writes counter = 6
  • P2 increments and writes counter = 6
  • Result: Counter should be 7, but it's 6 (lost update)

🟡 📚 Critical Sections

A critical section is a code segment that accesses shared resources and must not be executed by more than one process at a time. The critical section problem requires that:

  • Mutual Exclusion: Only one process can execute in its critical section at a time
  • Progress: If no process is in its critical section and some processes want to enter, one must be selected
  • Bounded Waiting: A process waiting to enter its critical section should not wait indefinitely

🟡 📚 Mutual Exclusion

Mutual exclusion ensures that only one process can access a shared resource at a time. This is fundamental to preventing race conditions and maintaining data integrity. Various mechanisms can achieve mutual exclusion:

  • Locks: Binary semaphores or mutexes that allow only one process to acquire the lock
  • Semaphores: Integer variables used to control access to shared resources
  • Monitors: High-level synchronization constructs that encapsulate shared data and operations
  • Atomic operations: Hardware-level operations that complete without interruption

🟡 🛠️ Semaphores

A semaphore is a synchronization variable that maintains a counter. It supports two atomic operations:

  • wait() (or P): Decrements the semaphore. If the value becomes negative, the process blocks
  • signal() (or V): Increments the semaphore. If there are waiting processes, one is awakened

There are two types of semaphores:

  • Binary Semaphore (Mutex): Can only be 0 or 1, used for mutual exclusion
  • Counting Semaphore: Can be any non-negative integer, used for resource counting

Semaphore Example

PSEUDOCODE 
// Binary semaphore (mutex) for mutual exclusion
semaphore mutex = 1;

// Process 1
wait(mutex);
    // Critical section
    shared_variable++;
signal(mutex);

// Process 2
wait(mutex);
    // Critical section
    shared_variable--;
signal(mutex);

Code Breakdown

Semaphore Initialization

PSEUDOCODE 
semaphore mutex = 1;

Initializes a binary semaphore (mutex) with value 1, meaning the resource is available. When a process calls wait(), it decrements the value. If the value becomes 0, the resource is locked. If another process tries to acquire it, the value becomes negative and the process blocks.

Entering Critical Section

PSEUDOCODE 
wait(mutex);
    // Critical section
    shared_variable++;

Before entering the critical section, the process calls wait(mutex) to acquire the lock. This ensures mutual exclusion - only one process can be in the critical section at a time. The process then safely modifies the shared variable.

Exiting Critical Section

PSEUDOCODE 
signal(mutex);

After completing the critical section, the process calls signal(mutex) to release the lock. This increments the semaphore value and wakes up any waiting processes, allowing them to enter their critical sections.

🟡 📚 Deadlock

A deadlock is a situation where two or more processes are blocked forever, waiting for each other to release resources. For a deadlock to occur, four conditions must be present simultaneously (Coffman conditions):

  • Mutual Exclusion: Resources cannot be shared
  • Hold and Wait: A process holds a resource while waiting for another
  • No Preemption: Resources cannot be forcibly taken from a process
  • Circular Wait: A circular chain of processes exists, each waiting for a resource held by the next
Example Deadlock Scenario:
  • Process P1 holds resource R1 and waits for resource R2
  • Process P2 holds resource R2 and waits for resource R1
  • Both processes are blocked indefinitely - deadlock occurs

🟡 📚 Starvation

Starvation occurs when a process is indefinitely denied access to resources it needs, even though other processes are making progress. Unlike deadlock, where all processes are blocked, starvation means some processes continue while others wait indefinitely.

Common causes of starvation include:

  • Unfair scheduling: Some processes are always prioritized over others
  • Resource allocation policies: Resources are allocated in a way that consistently favors certain processes
  • Priority inversion: Low-priority processes hold resources needed by high-priority processes

🔴 📚 Synchronization Algorithms

Various algorithms have been developed to solve the critical section problem and achieve process synchronization. These algorithms differ in their complexity, efficiency, and hardware requirements.

Peterson's Algorithm

Peterson's algorithm is a classic software-based solution for mutual exclusion between two processes. It uses shared variables to coordinate access without requiring special hardware instructions.

PSEUDOCODE 
// Shared variables
bool flag[2] = {false, false};
int turn = 0;

// Process i (i = 0 or 1)
do {
    flag[i] = true;
    turn = 1 - i;  // Give turn to other process
    while (flag[1-i] && turn == 1-i);  // Wait if other wants and has turn
        // Critical section
    flag[i] = false;
        // Remainder section
} while (true);

Bakery Algorithm

The Bakery algorithm extends Peterson's solution to N processes. It assigns each process a "ticket number" and processes enter their critical sections in ticket order, similar to customers in a bakery.

PSEUDOCODE 
// Shared variables
bool choosing[N] = {false};
int number[N] = {0};

// Process i
do {
    choosing[i] = true;
    number[i] = max(number[0], number[1], ..., number[N-1]) + 1;
    choosing[i] = false;
    
    for (int j = 0; j < N; j++) {
        while (choosing[j]);  // Wait if j is choosing
        while (number[j] != 0 && 
               (number[j] < number[i] || 
                (number[j] == number[i] && j < i)));  // Wait for turn
    }
        // Critical section
    number[i] = 0;
        // Remainder section
} while (true);

Dekker's Algorithm

Dekker's algorithm was one of the first software solutions for mutual exclusion between two processes. It uses flags and a turn variable to coordinate access.

🔴 📚 Advanced Synchronization Mechanisms

Monitors

A monitor is a high-level synchronization construct that encapsulates shared data and the operations that can be performed on it. Only one process can execute a monitor procedure at a time, providing automatic mutual exclusion.

Key features of monitors:

  • Encapsulation: Shared data and operations are grouped together
  • Automatic mutual exclusion: Only one process can be active in the monitor at a time
  • Condition variables: Allow processes to wait for specific conditions and be notified when conditions change

Message Passing

Message passing is an alternative to shared memory for inter-process communication and synchronization. Processes communicate by sending and receiving messages, which naturally provides synchronization.

Two main operations:

  • send(destination, message): Sends a message to a destination process
  • receive(source, message): Receives a message from a source process

Read-Write Locks

Read-write locks allow multiple readers or a single writer to access a resource. This is useful when reads are more frequent than writes, as it allows concurrent reads while maintaining exclusive access for writes.

📚 Summary

  • Process Synchronization coordinates multiple processes to prevent race conditions and maintain data consistency
  • Race conditions occur when processes access shared resources without coordination
  • Critical sections are code segments that must be executed atomically
  • Mutual exclusion ensures only one process accesses a resource at a time
  • Semaphores are synchronization variables that control resource access
  • Deadlock occurs when processes wait indefinitely for each other
  • Starvation happens when a process is indefinitely denied resources
  • Synchronization algorithms (Peterson's, Bakery, Dekker's) provide software solutions for mutual exclusion
  • Advanced mechanisms like monitors and message passing offer higher-level synchronization abstractions
