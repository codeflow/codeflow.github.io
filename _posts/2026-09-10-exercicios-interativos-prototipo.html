O que você vai encontrar neste artigo
  • O Lab: uma gaveta, ao lado de Sumário e Ajuda, com todos os exercícios do post, navegação por fichas e progresso.
  • Em cada seção, um link abrir no Lab que leva direto ao exercício daquele tópico; no Lab, um link de volta para a seção.
  • Cinco tipos de exercício: Java com regras, Java com lacunas, JavaScript executado, múltipla escolha e resposta em texto.
  • Como o autor declara um exercício e o que ainda falta decidir (compilar Java de verdade exige backend ou JVM no navegador).

O Codeflow é um site estático servido pelo GitHub Pages: não existe servidor para compilar o que o leitor digita. Toda a validação, portanto, acontece no navegador. Os exercícios não ficam espalhados pelo texto: moram no Lab, a gaveta que abre pelo botão do cabeçalho ou pela aba na margem direita, ao lado de Sumário e Ajuda. Cada seção do artigo aponta para o seu exercício, e cada exercício aponta de volta para a seção.

1. Três níveis de validação num site estático

AbordagemLinguagensO que validaLimite
Regras sobre o códigoQualquerAssinatura, construções obrigatórias ou proibidas, chaves balanceadas, ponto e vírgulaNão compila — aceita código que segue as regras mas está errado
LacunasQualquerCada lacuna contra uma lista de respostas aceitas ou uma expressão regularPreciso — mas o exercício é fechado por natureza
Execução com testesJavaScriptRoda o código e compara o resultado de chamadas com o valor esperadoReal — só para JavaScript; precisa de sandbox antes de publicar
Múltipla escolha e textoQualquerAlternativas marcadas ou resposta curta contra o gabarito (sem acentos e maiúsculas)Preciso — para conceitos, não para código
Backend de compilaçãoJava, Python, C…Compila e executa de verdade com testes de unidadeExige serviço — API externa (Piston, JDoodle) ou um servidor próprio
JVM no navegadorJavaCompila e executa Java via CheerpJ ou TeaVM, sem servidorPesado — dezenas de MB carregados na primeira execução

2. Java com regras: implemente o método

O leitor escreve o método inteiro. O validador não compila: aplica uma lista de verificações declaradas pelo autor (assinatura, uso de determinadas construções, ausência de outras, chaves balanceadas e ponto e vírgula nas instruções). Cada verificação vira uma linha do resultado, com uma dica quando falha. Espaços, quebras de linha, comentários e nomes de variáveis não importam; só as construções exigidas.

Pratique: abrir no Lab: Exercício 2, palíndromo

▼O que esse nível não pega
Um código que use charAt, toLowerCase e return true; sem lógica nenhuma passa em todas as regras. As regras servem para guiar o leitor ("faltou normalizar", "faltou o return"), não para provar que o método está correto. Para exercícios em que a corretude importa, o caminho é a execução (nível 3) ou um backend de compilação.

3. Java com lacunas: complete o código

O autor escreve o código com marcadores ___; o componente transforma cada um em um campo. A validação é exata por lacuna: cada uma tem uma lista de respostas aceitas ou uma expressão regular. Funciona para qualquer linguagem porque não depende de compilar, e é a forma mais confiável de exercitar sintaxe (palavras-chave, tipos, operadores).

Pratique: abrir no Lab: Exercício 3, laço de contagem

4. JavaScript executado: o código roda de verdade

Quando a linguagem do exercício é JavaScript, o navegador é o próprio interpretador. O componente executa o que o leitor escreveu e compara o resultado de cada chamada de teste com o valor esperado — o mesmo princípio de um teste de unidade. Aqui a validação é real: qualquer implementação que devolva os valores certos passa; código bonito mas errado falha nos testes.

Pratique: abrir no Lab: Exercício 4, fatorial

▼Antes de publicar: sandbox e limite de tempo
No protótipo o código roda na própria página. Um laço infinito trava a aba, e o código tem acesso ao DOM. A versão publicável deve executar dentro de um iframe com sandbox ou de um Web Worker, com limite de tempo (por exemplo, 2 segundos) e sem acesso à página. É uma mudança só no componente; os exercícios continuam iguais.

5. Como o autor declara um exercício

Os exercícios ficam num bloco <div class="cf-lab" hidden> depois do artigo. O script /assets/js/exercise.js, carregado pelo layout de todo post, move esse bloco para a gaveta do Lab, mostra a aba e o botão, monta as fichas de navegação e liga os links cf-labLink das seções. Cada exercício é um .cf-exercise com data-kind (o tipo), data-section (a seção a que pertence, para o link de volta) e um JSON com as verificações e a solução. O esqueleto do Exercício 2:

exercicio.html — HTML + JSON
<!-- na seção do artigo -->
<p>Pratique: <a class="cf-labLink" href="#lab-ex2">abrir no Lab: Exercício 2</a></p>

<!-- depois de </div><!-- /cf-article -->, antes de <!-- references --> -->
<div class="cf-lab" hidden>
  <div class="cf-exercise" id="ex2" data-kind="code" data-lang="Java" data-section="sec2">
    <div class="exHdr">Exercício 2 — palíndromo <span class="lang">— Java</span></div>
    <p class="exTask">Enunciado.</p>
    <div class="exEditor"><pre class="exGutter"></pre><textarea spellcheck="false">código inicial</textarea></div>
    <div class="af-buttonBar">
      <button class="af-button" data-act="check">Validar</button>
      <button class="af-button" data-act="reset">Recomeçar</button>
      <button class="af-button" data-act="solution">Ver solução</button>
    </div>
    <div class="exResult" hidden></div>
    <script type="application/json" class="exSpec">{
      "checks": [
        { "type": "regex",      "pattern": "\\breturn\\b", "msg": "Devolve um resultado", "hint": "Falta o return." },
        { "type": "regex",      "pattern": "System\\.out", "absent": true, "msg": "Não imprime nada" },
        { "type": "balanced",   "msg": "Chaves e parênteses balanceados" },
        { "type": "semicolons", "msg": "Instruções terminam com ponto e vírgula" }
      ],
      "solution": "public static boolean ehPalindromo(String s) { ... }"
    }</script>
  </div>
</div>
  • data-kind="code" usa checks: regex (com absent: true para proibir algo), balanced e semicolons. Os padrões são aplicados ao código sem comentários e com espaços colapsados.
  • data-kind="blanks" usa <pre class="exBlanks"> com ___ e uma lista blanks, uma entrada por lacuna: accept (lista) ou regex, mais hint e width.
  • data-kind="run" usa tests: call é a expressão executada e expect o valor esperado (comparado como JSON, então funciona com números, strings, arrays e objetos).
  • data-kind="quiz" usa <ul class="exOptions"> com input do tipo radio (uma resposta) ou checkbox (várias) e answer com os índices corretos, a partir de 0, mais explain mostrado depois de validar.
  • data-kind="text" usa <input class="exText"> e accept (lista, comparada sem acentos, maiúsculas e espaços extras) ou regex, mais hint e explain.
  • O texto dos botões é escrito no idioma do post; as mensagens do resultado ("3 de 5 verificações passaram", "2 de 5 concluídos") vêm do script, em en, pt-BR e es.

Confira: abrir no Lab: Exercício 5, resposta em texto

6. O que falta decidir

  • Java de verdade ou regras? Se os exercícios de Java precisam provar corretude, é preciso escolher entre uma API de compilação (custo, dependência externa, chave de API exposta ou proxy) e uma JVM no navegador (CheerpJ carrega dezenas de MB, mas funciona sem servidor).
  • Progresso do leitor. A tentativa e os exercícios concluídos ficam no localStorage do navegador; o Lab mostra "n de m concluídos" e marca as fichas. Não há conta de usuário.
  • Validador do site. Se o formato for aprovado, o validate_post.py pode ganhar uma checagem LAB: JSON válido, todo cf-labLink apontando para um exercício existente, e solução que passa nas próprias verificações e testes.
  • Template e skill. O /codeflow post passaria a gerar a seção de exercícios e o bloco cf-lab quando o post for prático.
